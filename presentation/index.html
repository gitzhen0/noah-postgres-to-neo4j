The Problem

Relational databases optimize for storage, not for relationships.

PostgreSQL · 21 lines · 174.4 ms
-- "All ZIPs within 2 hops of 10001"
WITH RECURSIVE reachable(zip_code, depth) AS (
  SELECT zip_code, 0
  FROM   zip_shapes
  WHERE  zip_code = '10001'
  UNION
  SELECT CASE WHEN a.zip_code = r.zip_code
              THEN b.zip_code ELSE a.zip_code END,
         r.depth + 1
  FROM   reachable r
  JOIN   zip_shapes a
  JOIN   zip_shapes b
         ON  a.zip_code < b.zip_code
         AND ST_Touches(a.geom, b.geom)
    ON   r.zip_code IN (a.zip_code, b.zip_code)
  WHERE  r.depth < 2
)
SELECT DISTINCT zip_code, MIN(depth)
FROM reachable
GROUP BY zip_code;
Neo4j · 4 lines · 4.6 ms
// same question
MATCH path = (z:ZipCode {zip_code:'10001'})
              -[:NEIGHBORS*0..2]-(n:ZipCode)
WITH  n.zip_code AS zip_code,
      min(length(path)) AS min_depth
RETURN zip_code, min_depth
ORDER BY min_depth, zip_code;
Same question. Different paradigm. 5× less code, 37× faster runtime. The gap widens as the query graph deepens — and so does the gap in who can actually write the query.

Built on published research

Three papers, synthesized into a production-ready pipeline.

FORMAL MODEL
De Virgilio et al., 2013
ACM GRADES Workshop
Formal conversion rules: tables → nodes, foreign keys → relationships, join tables → direct edges. Exploits RDBMS constraints to preserve semantic integrity.
AUTOMATION
Rel2Graph
Zhao et al., 2023 · arXiv:2310.01080
Automated knowledge graph construction from multiple relational sources, validated on Spider / KaggleDBQA benchmarks. Proves the pipeline shape scales beyond a single schema.
TOOLING
Data2Neo
Minder et al., 2024 · arXiv:2406.04995
Open-source Python patterns for incremental Neo4j loading with configurable mapping. Operational blueprint for batch MERGE with idempotency.
My contribution: synthesize all three into a single config-driven pipeline, add an LLM-powered schema interpreter, and validate on a real PostGIS dataset.

Performance · PostgreSQL vs Neo4j · 10 queries

Right tool for the right query shape.

Read: the dashed line is parity. Bars right = Neo4j faster; bars left = PG faster. Flat queries over indexed columns are PostgreSQL's home turf — we don't claim otherwise. Path-shaped queries are Neo4j's home turf, and the advantage grows with hop depth.
90s. The honesty move: I could have picked 10 queries where Neo4j wins. I chose 10 that span both home turfs. The point of the architecture isn't that graph is always faster — it's that the right query shape matches the right engine. var-path is what Neo4j is for. That's why the next slide zooms in on Q9.
The query that defines the architecture

"All ZIPs within 2 hops of 10001" — 37.7× faster.

Why graph wins here
  • Path-shaped query — expressed natively as a pattern, not approximated by joins.
  • Pre-computed edges — NEIGHBORS was materialized at migration time; query is O(edges), not O(n²).
  • No plan blowup — depth is a parameter, not a schema change. Extending to 3-hop is swapping *0..2 → *0..3.
  • Readable — 4 lines a domain expert can review; 21 lines of recursive SQL, most can't.

Honest inventory

What this project doesn't claim to solve.

  • Data completeness
    35 housing projects carry postcodes outside NYC's 177-ZIP set (adjacent NJ/PA, PO boxes). Documented in audit; no relationship created. Reasonable engineering call — silently inventing a ZIP node for them would be worse.
  • Data substitution
    Two AffordabilityAnalysis properties are null (median_rent_usd, rent_to_income_ratio): original spec called for StreetEasy's proprietary feed. Substituted ACS 2022 B25070 rent-burden rate after sponsor sign-off — equivalent policy signal, publicly available.
  • Performance scope
    Neo4j wins on path queries, not on flat aggregations. I don't claim "Neo4j is faster than PostgreSQL" — that framing is wrong. Tested at NOAH scale (~10k nodes); the gap scales superlinearly with hop depth and graph density. At 100M-node scale the story would be different.
  • LLM dependencies
    Text2Cypher requires an Anthropic or OpenAI API key. Offline inference via local models (Llama, Qwen) would be next — schema-aware prompt is provider-agnostic, so it's a 1-week swap.
60s. Preempt every critique. Audit, data, perf, LLM — name the boundary before they do. This slide earns more credibility than any "results" slide.
Three things I'd tell next semester's cohort

Lessons learned.

  • 1 · Config > Code
    Early versions hardcoded NOAH table names everywhere. Moving to a single mapping_rules.yaml was the single biggest quality jump — it turned a one-off script into a reusable tool. Every domain-specific string you delete is a future demo you enable.
  • 2 · Benchmarks tell the story
    My first performance comparison had 8 queries, 7 of which were flat aggregations. Neo4j lost 7 of 8 and I wrote "1.6× speedup" as the headline, which was misleading cherry-picking. Rebuilding around five categories — 2 queries each, spanning PG home turf and Neo4j home turf — turned a defensive story into an honest one with a genuine 37× hero case.
  • 3 · LLM schema interpretation is a force multiplier
    The first NOAH mapping took me ~6 hours of manual yaml writing. The second pass with main.py interpret (Claude reads pg_catalog, returns a draft yaml with confidence scores) took 30 seconds + 45 minutes of review. For Chinook, that workflow converged in 15 minutes end-to-end. It's not about replacing the engineer, it's about erasing the boring first 80%.
75s. End with lessons, not with results. Shows reflection, shows growth. The middle lesson is a quiet confession — that's the credibility move.
